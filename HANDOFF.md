## 1. Что за проект

Делаем `soup-connectome` — **портируемый рантайм для запуска биологического
коннектома** (MaleCNS, мозг самца дрозофилы) на любом доступном железе: CPU,
NVIDIA CUDA, слабый GPU через streaming, браузер через WebGPU/WASM, позже —
кластер.

Идея взята у проекта Soup (LLM fine-tuning, того же автора): **модель не обязана
целиком помещаться в VRAM**. Только вместо decoder-слоёв мы стримим блоки
разреженных синаптических связей.

**Позиционирование — это инфраструктура, а не демка.** Не «мы заставили мозг мухи
играть в Doom» (это уже сделали другие, поздно), а «мы сделали первый portable
runtime, который запускает реальный коннектом на любом железе — пусть медленно,
но воспроизводимо».

## 5. Два неудобных факта — держи их в голове, они меняют позиционирование

### 5.1 MaleCNS, вероятно, НЕ требует streaming на 8 GB GPU

Оценка по размеру файла (1.1 GB feather, колонки ≈ `body_pre:int64`,
`body_post:int64`, `weight:int32`) → **~50–60M рёбер** *(ОЦЕНКА, проверить при
скачивании)*. В упакованном виде `indices:int32 + weights:int16` = 6 байт/ребро →
**~350 MB**. Целиком влезает в 8 GB VRAM.

Это не ломает проект, а уточняет тезис. Честная формулировка:

> MaleCNS влезает резидентно в 8 GB. Streaming — это то, что позволяет запустить
> его на 2 GB, во вкладке браузера и на следующем коннектоме, который будет
> в 100 раз больше.

Не продавай решение несуществующей проблемы.

### 5.2 Наивный streaming ловит ровно ту патологию, которую Soup сам запрещает

В `layer_stream.py` Soup прямым текстом исключает GRPO/PPO:

> *Generation rollouts re-read every layer once per generated token, which destroys
> the whole premise: streaming amortises one weight read over a training step, not
> over a single decoded token.*

Симуляция спайков — тот же паттерн: каждый timestep хочет перечитать весь граф.
При 350 MB и ~20 GB/s это ~57 шагов/с → при dt=1 мс **0.057× реального времени**
*(ОЦЕНКА, не измерено)*.

**Решение — синаптические задержки.** В реальном коннектоме аксонная задержка ≥ 1
шага. Если минимальная задержка D шагов, спайки, испущенные сейчас, приземлятся
только через D шагов — значит один визит к блоку амортизируется на D timestep'ов
через delay-line буферы. При D=10 → ~570 шагов/с. Биологически мотивировано.

## 6. Предложенный дизайн

**Статус: представлен пользователю, но явно НЕ утверждён.** Пункты 6.1 и 6.3
помечены как спорные — предыдущий агент осознанно отошёл от исходной формулировки
пользователя. **Подтверди их до написания кода.**

### 6.1 Каноническая арифметика — определяется самым слабым бэкендом (ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ)

Главный принцип:

> Канонические численные операции — это то, что **WebGPU умеет делать точно**.
> WGSL не имеет `i64`. Значит вся симуляция живёт в `int32`.

| Величина | Тип | Замечание |
|---|---|---|
| Мембранный потенциал `V` | `int32`, scale `2^16` | 16 дробных бит |
| Вес синапса `w` | `int16` | число синапсов, знак от нейромедиатора |
| Порог, reset, рефрактерность | `int32` / `uint8` | |

Затухание — **без умножения**: `V -= V >> k`, что точно равно умножению на
`(1 − 2⁻ᵏ)` с усечением. Для тонкой настройки — композиция: `V -= (V>>k1) + (V>>k2)`.

Почему не `V * DECAY_NUM >> SHIFT`: умножение переполняет `int32` и требует
`int64`-промежуточного, которого в WGSL нет. Сдвиговая форма не переполняется
никогда и даёт побитово одинаковый результат на CPU, CUDA и WebGPU.

**Цена:** постоянные затухания берутся из дискретного множества, а не любые.
Это документируемое ограничение, купленное за настоящий бит-в-бит паритет.
**Это спорный пункт — подтверди у пользователя.**

Целочисленное сложение ассоциативно → порядок редукции на GPU не важен, атомарные
`atomicAdd` по `int32` при scatter точны. Именно это делает паритет достижимым;
с float он был бы недостижим в принципе.

### 6.2 Каноническая раскладка графа — CSR по источнику

Активность разрежена (единицы Гц) → event-driven push: «нейрон j спайкнул →
разослать по исходящим» → **CSR, индексированный источником** (out-edges).
CSC добавить позже только для анализа, не для симуляции.

Формат на диске — mmap-пригодная директория, по образцу шардов Soup:

```
graph.scx/
  manifest.json      # версия, N, E, scale-факторы, провенанс, sha256 каждого блока
  neurons.bin        # id, тип, нейромедиатор, сторона
  blocks/
    block_00000.scb  # непрерывный диапазон нейронов-источников + их рёбра
    block_00001.scb
```

Конвертация держит в RAM **один блок**, а не весь граф — калька с принципа Soup
«Peak RSS while sharding is ONE decoder layer, not the model».

### 6.3 Режимы — три ортогональные оси вместо пяти смешанных имён (ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ)

Исходные пять уровней пользователя (`portable / compact / accelerated / streamed /
full`) смешивают три независимых понятия. Предложено развести, имена оставить как
**пресеты**:

| Ось | Значения |
|---|---|
| `--device` | `auto` / `cpu` / `cuda` / `webgpu` |
| `--residency` | `resident` / `streamed` |
| `--scope` | `full` / `compact` |

`portable` = cpu+resident+compact, `full` = любое устройство+resident+full и т.д.
Тогда `--device cuda --residency streamed` читается однозначно, а «accelerated» и
«streamed» перестают выглядеть взаимоисключающими, хотя таковыми не являются.
**Это спорный пункт — подтверди у пользователя.**

### 6.4 Структура пакета

```
src/soup_connectome/
  graph/     format.py  builder.py  example.py     # канонический формат, без torch
  sim/       lif.py  planner.py                    # fixed-point семантика + планировщик
  backends/  base.py  cpu.py  cuda.py  webgpu.py   # closed allowlist, не эвристика
  cli.py                                           # typer + rich
```

`planner.py` считает VRAM и пропускную способность **без импорта torch**, чтобы
`soup-connectome plan` работал на машине вообще без GPU — прямая калька с
planner/runtime split в Soup.

### 6.5 Тесты

- Золотые спайк-поезда на примере графа (бит-точная фикстура)
- Round-trip формата, детект переполнения/насыщения
- CPU↔CUDA паритет (skip без GPU)
- **`streamed` побитово равен `resident`** — самый сильный тест проекта:
  превращает «streaming работает» из утверждения в проверяемый факт

## 7. Конвенции, наследуемые от Soup

- `typer` + `rich` для CLI, **никогда** голый `print()`
- `pydantic v2` как единственный источник правды для конфига
- **Лёгкое ядро**: `torch` и прочее тяжёлое — в extras (`[cuda]`), не в основных зависимостях
- **Ленивые импорты** тяжёлого внутри функций, никогда на верхнем уровне модуля
- `ruff`, line length 100, правила `E, F, I, N, W`
- Python 3.10–3.12 (верхняя граница осознанная, как в Soup)
- **Закрытые allowlist'ы вместо эвристик** — полуподдержанный бэкенд должен падать, а не тихо врать
- Path containment через `os.path.realpath` + `os.path.commonpath`, не `Path.resolve()`
- **Честная маркировка констант прямо в докстрингах** — образец из `layer_stream.py`:
  «A chosen safety margin, not a measured bound». Каждое число помечается
  `measured` / `estimated` / `not tested`.

## 9. Чего НЕ делать

- Не утверждать, что нынешний Soup уже умеет симулировать коннектомы. Это **новый
  отдельный модуль**, построенный на идеях Soup. Нынешний Soup доказан для layer
  streaming при fine-tuning — и только.
- Не выдумывать бенчмарки. Каждое число — `measured`, `estimated` или `not tested`.
- Не скачивать большие файлы автоматически. Только по явной команде пользователя.
- Не скачивать EM-объём изображений (12.7 GB / 6.8 GB файлы) вообще.
- Не симулировать детальную биологическую морфологию.
- Не строить сложный UI, пока рантайм не работает.
- Не заявлять биологическую точность без научной валидации.
- Не вливать это в основной репозиторий Soup, пока прототип не стабилен.
- Не делать тихий фолбэк с CUDA на CPU — бэкенд, которого нет, должен честно
  сказать «not implemented».
